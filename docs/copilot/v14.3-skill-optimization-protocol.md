# V14.3 Skill 优化分析协议

本协议供开发者或 Codex 对已有 Evaluation Run 做可重复、只读、有证据的分析。分析过程不得自动修改、
审核、发布或回滚 Skill，不得执行业务 Tool。若没有 Run 数据，结论必须是“没有可分析数据”。

## 1. 稳定分析入口

输入至少包含：`tenant_id`（由当前身份确定）、`run_id`，可选 `baseline_run_id`。不得接受请求体注入
其他租户 ID。优先使用现有只读 API：

- `GET /api/v1/evaluations/runs/{run_id}`：运行配置和 Case；
- `GET /api/v1/evaluations/runs/{run_id}/metrics`：聚合指标；
- `GET /api/v1/evaluations/runs/{run_id}/skill-diagnostics`：失败分类；
- `GET /api/v1/evaluations/runs/{run_id}/skill-report`：V14.3 机器可读总入口；
- `GET /api/v1/evaluations/comparisons/{id}`：已经创建的基线比较。

`skill-report` 返回 protocol、run/config/environment fingerprint、metrics、diagnostics 和经脱敏的 Case trace。
它不返回 JWT、Secret、完整内部 Prompt、其他租户 Catalog 或不受控原始 Tool 数据。

```powershell
curl.exe "http://localhost:8013/api/v1/evaluations/runs/<RUN_ID>/skill-report" `
  -H "Authorization: Bearer <EVALUATION_READ_TOKEN>" `
  -H "X-Tenant-ID: <TEST_TENANT>"
```

没有“最近一次”专用 API 时，先用 `GET /evaluations/runs?page=1&page_size=20`，按服务端返回顺序选择
已结束且目标模式匹配的 Run，再用明确 run_id 分析。列表为空、Run 未结束或报告无 Case 时停止，不猜测。

## 2. 必读源码

按问题逐层读取，避免浏览无关模块：

1. `app/services/evaluations.py`：Run 快照、Runner、报告；
2. `app/evaluation/metrics.py`：实际分子、分母和缺失值处理；
3. `app/skills/catalog.py`：Catalog 查询和过滤原因；
4. `app/skills/selector.py`：召回、阈值和选择方法；
5. `app/skills/chat.py`：选择 trace、Pending 和 Chat 生命周期；
6. 若进入运行阶段，再读 `skills/loader.py`、`services/skill_execution.py`、
   `graph/multi_agent.py`、`tools/executor.py`；
7. 版本或导入问题再读 `skills/parser.py` 与 `services/ecosystem.py`。

不要从文档推断代码行为；文档与报告冲突时，以当前代码、迁移版本和 Run 快照为准。

## 3. 可比性门禁

比较两个 Run 前逐项确认：

- 相同 `dataset_version_id` 与 content hash；
- 相同 execution_kind（REPLAY、SELECTOR_LIVE、END_TO_END 不可混比）；
- 相同租户、权限快照和 SkillVersion 集合，除非版本正是实验变量；
- 相同 Selector Profile、阈值、Top-K、是否允许 LLM，除非该项是实验变量；
- 相同模型 provider/name/config、环境 fingerprint 和 Feature Flags；
- 相同 READY/跳过 Case 口径；
- Run 已到终态，缺失数据比例可解释。

若多个变量同时变化，只能报告相关性，不能归因。模型温度或 Provider 非确定性存在时，至少运行多次，
报告均值、离散程度和逐 Case 一致性；一次波动不能直接定义为系统缺陷。

## 4. 分析顺序

1. 验证 Run 存在、租户可见、状态终结、模式和依赖；
2. 读取总数、成功、失败、跳过及缺失数据；
3. 按错误分类计数并排序，不从一条 Case 外推全部；
4. 对最高频类别抽取代表 Case，关联 Expected Result、actual、Selection Trace；
5. 按 Catalog → Recall → Select → Input → Loader/Plan → Tool → Evidence → Output 定位首个失败阶段；
6. 检查建议是否与该阶段直接相关；
7. 有 baseline 时通过可比性门禁后计算绝对差和相对差；
8. 输出验证计划和风险，不执行修改。

## 5. 事实到建议的映射

| 证据 | 可支持的建议 | 不应建议 |
| --- | --- | --- |
| 正确 Skill 被 Catalog 过滤 | 查审核/启用/IAM/租户/风险 | 改 LLM Prompt |
| Catalog 有、Top-K 无 | 改 Metadata、分词、Top-K 或评估 Embedding | 改 Tool 参数 |
| Top-K 有、最终选错 | 校准规则/阈值/LLM 裁决 | 改 Evidence |
| 选择正确、INPUT_MISSING | 改 Schema 描述、确定性抽取、Pending | 扩大候选 |
| LOAD/REFERENCE 失败 | 查版本快照、资源路径、大小和依赖 | 改召回阈值 |
| TOOL_ARGUMENT_INVALID | 对齐 input/tool schema 和参数映射 | 改 Embedding |
| PERMISSION_DENIED | 查 IAM/资源边界；不能放宽 Skill 绕过 | 给 manage 权限 |
| EVIDENCE_INVALID | 查 ToolRun 来源、引用和复核 | 伪造引用 |
| TIMEOUT/BUDGET | 分段延迟、调用数、Reference 和模型用量 | 把未知成本写 0 |

每条建议必须包含：Run ID、失败类别、受影响 Case 数/分母、代表 Case key、对应 trace 字段、建议改动、
预期改善指标、必须回归的 Case 集合和风险。

## 6. 系统缺陷与模型随机性

确定性 Parser、权限过滤、Schema、版本绑定、Tool 白名单在相同输入下不一致，优先视为系统缺陷。
同一个正确 Top-K 在同模型配置下仅 LLM 裁决波动，可能是模型随机性；需重复运行后判断。下游 HTTP 超时
属于依赖故障，不能归因 Selector。Expected Result 本身含糊或业务真值不足时标记数据集问题，不用模型输出
反向制造真值。

## 7. 版本与回归规则

修改 description、instructions、Schema、agents/tools/permissions、Evidence、Reference、预算或依赖，必须创建
新 SkillVersion，经过审核和测试租户启用。仅修改 Selector 通用算法/阈值不创建 SkillVersion，但必须固定新的
selector config version。数据真值变化创建新的冻结 DatasetVersion，不改已冻结版本。

以下改动必须回归全部 120 Case 及安全集：Selector/召回、Catalog 过滤、ToolExecutor、IAM、Pending、DAG、
Evidence、Chat/SSE。仅文案修复可先跑邻近 Skill 集，但发布前仍跑 NO_SKILL、相似描述、权限和 Injection。

## 8. 输出格式

```json
{
  "analysis_protocol": "v14.3",
  "run_id": 123,
  "baseline_run_id": 122,
  "data_status": "AVAILABLE",
  "comparability": {"comparable": true, "differences": []},
  "top_failure_stages": [
    {"stage": "RECALL", "category": "SKILL_NOT_SELECTED", "cases": 8, "denominator": 120}
  ],
  "evidence": [
    {"case_key": "skill-paraphrase-001", "expected": ["inventory-analysis"], "candidates": []}
  ],
  "recommendations": [
    {
      "priority": 1,
      "change_scope": "SKILL_VERSION",
      "reason": "正确 Skill 未进入候选",
      "verify_with": ["skill-paraphrase-*", "no-skill-*", "similar-description-*"]
    }
  ],
  "unknowns": ["真实成本未上报"],
  "prohibited_actions_taken": []
}
```

没有数据时使用：

```json
{
  "analysis_protocol": "v14.3",
  "data_status": "NO_DATA",
  "conclusion": "没有可分析的已完成 Skill Evaluation Run",
  "recommendations": [],
  "next_action": "创建并完成 REPLAY 或 SELECTOR_LIVE Run 后重新分析"
}
```

不得把未知 token/cost/latency 填 0，不得把 LEXICAL score 称为概率，不得输出无事实依据的“优化后预计提升
X%”。

## 9. 发布与回滚决策

候选版本只有在目标指标改善、FPR/权限违规/写操作为零、安全集无回归、P95 和预算满足门禁时才建议灰度。
报告只给建议，不调用审核、enabled、rollback API。灰度由有管理权限的人执行并记录审批。异常时回滚到已知
版本；仓库实现会创建受控的回滚当前版本且要求重新审核，历史 SkillRun 仍指向旧 version_id。

## 10. 当前能力边界

- 报告 API 是只读、租户隔离的稳定入口；没有自动修改或发布能力；
- SELECTOR_LIVE 运行真实 PostgreSQL Catalog 和真实 Selector，但不执行 Loader/Tool；
- END_TO_END 因专用服务身份和真实依赖尚未配置而明确 BLOCKED；
- 当前召回为 LEXICAL，不存在 Skill Embedding 指标真值；`embedding_calls` 只有真实调用来源时才可统计；
- 本地环境若无 PostgreSQL/Redis，不能分析“最近一次”数据库 Run；先按测试手册准备环境。

后续标准请求示例：

> 按照 V14.3 优化协议，读取 Run 123 的 skill-report；若有可比 Baseline 则先通过可比性门禁。列出失败最多
> 的首个阶段、代表 Case、证据字段和优先建议。不要修改或发布任何 Skill；没有数据就明确返回 NO_DATA。
