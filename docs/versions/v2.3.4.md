# V2.3.4 — RBAC 管理后台完整闭环

## 1. 业务目标

补全企业后台对成员、角色、权限的管理闭环。不重新设计 RBAC、JWT、TenantContext 或 Wujie。

本版本完成后：

- 成员可添加已有账号、代建新账号、查看、改角色、启用、禁用、移出企业。
- 角色可创建、查看、编辑自定义角色、删除未使用的自定义角色、配置权限。
- 权限目录只读展示系统当前支持的 PermissionCode。
- 管理员代建账号使用一次性临时密码；首次登录必须改密。

不进入 V3 / 商品 / 订单 / 库存实际业务。OWNER 转移仍为后续独立流程。当前没有 `operation_logs` 表，本版不引入审计系统。

## 2. User 与 TenantMember

| | User | TenantMember |
| --- | --- | --- |
| 含义 | 平台全局登录账号 | 该 User 在某一家企业里的成员身份 |
| 范围 | 无 `tenant_id`，一人可加入多家企业 | 必有 `tenant_id` |
| 企业能否删除 | 不能。企业不能删除全局 User | 可以移除，只解除本企业关系 |
| 邮箱 | 全局身份，成员编辑不能改 | 只展示，不在成员接口里改 |

新增成员两种模式：

1. 添加已有账号：按 email 查找 User → 创建 TenantMember + MemberRoleGrant。
2. 创建新账号：同一事务创建 User + TenantMember + 角色授权。临时密码只在创建成功响应里出现一次。

## 3. PermissionCode 与 RolePermission

- `PermissionCode`：系统代码真正支持哪些权限。写在 `app/core/permissions.py`。
- `permissions` 表：平台权限目录，由 seed / 迁移同步，租户管理员不能增删改。
- `role_permissions`：某个租户角色实际拥有哪些目录项。

新增业务功能时：开发人员加 PermissionCode → seed 同步 permissions 表 → 管理员在角色权限界面勾选。前端不硬编码权限表，也不允许任意输入 code。

## 4. 系统角色与自定义角色

系统预置：`OWNER` / `ADMIN` / `OPERATOR` / `WAREHOUSE` / `VIEWER`，`is_system=true`，禁止删除。`is_system` 不等于拥有全部权限。

| 角色 | 改名称 | 改权限 | 删除 |
| --- | --- | --- | --- |
| OWNER | 禁止 | 禁止（核心权限冻结） | 禁止 |
| ADMIN | 禁止 | 允许调业务权限，必须保留租户管理能力 | 禁止 |
| OPERATOR / WAREHOUSE / VIEWER | 禁止 | 允许按目录调整 | 禁止 |
| 自定义 | 允许 | 允许 | 无人使用时允许 |

删除仍被占用的自定义角色返回 `40041 ROLE_IN_USE`，文案含成员人数。不会静默删除 MemberRoleGrant。

## 5. 成员创建流程

添加已有账号：`POST /api/v1/tenants/{id}/members`

1. 按 email 查 User，不存在 `40411`。
2. 已是本企业成员 `40911`。
3. 校验全部 role_id 属于当前租户，禁止 OWNER。
4. 同一事务写 TenantMember + MemberRoleGrant。

创建新账号：`POST /api/v1/tenants/{id}/members/accounts`

1. 先校验角色（避免 User 已占用邮箱唯一键后才发现角色非法）。
2. `secrets` 生成一次性临时密码，只存 Argon2id。
3. User.`must_change_password=True`。
4. 同一事务：User → TenantMember → 角色。任一步失败 rollback。
5. 明文临时密码只出现在本次响应的 `temporary_password`。列表/详情不再返回。不写日志、不写 localStorage。

首次登录后，除 `GET /auth/me` 与 `POST /auth/change-password` 外，业务接口返回 `40350`。

## 6. 角色权限配置流程

1. `GET /api/v1/permissions` 拉取目录，按 `module` 分组勾选。
2. `PUT /api/v1/roles/{role_id}/permissions` 提交 `permission_ids`。
3. 后端校验租户、角色归属、Permission 存在、OWNER/ADMIN 保护。
4. 同一事务删除旧 `role_permissions` 再插入新集合。
5. 无权限缓存：提交后下一次 `require_permission` / `my-permissions` 立即按新库数据判定。
6. 前端失效角色列表、角色详情、`my-permissions` Query，菜单和按钮随新编码重算。

## 7. OWNER 保护

禁止：删除 OWNER 角色、通过普通接口改 OWNER 权限、通过普通成员接口授予或移除 OWNER、禁用最后一个有效 OWNER。

`TenantMember.role = OWNER` 与 OWNER 系统角色同时存在，判定时任一成立即视为所有者。所有权转移本版不做。

## 8. 数据库迁移

`20260928_0005_user_must_change_password`：`users.must_change_password` BOOLEAN NOT NULL DEFAULT 0。

不新增成员/角色表。不引入 operation_logs。
