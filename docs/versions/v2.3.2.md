# V2.3.2 企业成员与角色授权

## 1. 业务目标

在现有多租户 RBAC 上，打通「查看成员 → 按邮箱添加已注册用户 → 分配角色 → 权限立即生效 → 启停成员」的完整闭环，并提供 ERP 成员管理、角色管理页面。

不发送邀请邮件。不自动注册账号。不实现 OWNER 转移。不改 Wujie 生命周期。

## 2. 完整业务流程

1. 管理员打开 ERP「系统管理 / 成员管理」。
2. 后端按当前 `TenantContext` 返回本企业成员（含 RBAC 角色）。
3. 管理员输入已注册邮箱并选择角色（可多选，不含 OWNER）。
4. 同一事务写入 `tenant_members` 与 `member_roles`。
5. 管理员修改角色时，先校验全部 `role_id` 属于当前租户，再行锁成员并全量替换授权。
6. 被改角色的用户下一次请求从数据库重算权限；Access Token 未过期也不能沿用旧权限。
7. 禁用成员后，`get_tenant_context` 立刻返回 40310。

## 3. 数据库变更

无新表、无新迁移。复用 V2.3.1 的 `tenant_members` / `roles` / `member_roles` / `permissions` / `role_permissions`。

并发策略：添加成员依赖 `UNIQUE(tenant_id, user_id)`；改角色对成员行 `SELECT ... FOR UPDATE`。

## 4. API 变更

保持 `/api/v1/tenants/{tenant_id}/members` 契约，避免第二套 `/current/members`。路径中的 `tenant_id` 必须等于 `X-Tenant-ID`。

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/tenants/current` | 有效成员 | 新增 `permission_codes` |
| GET | `/tenants/{id}/members` | `tenant:member:read` | 分页列表，含 `roles` |
| POST | `/tenants/{id}/members` | `tenant:member:manage` | `email` + `role_ids` |
| GET | `/tenants/{id}/members/{member_id}` | `tenant:member:read` | 详情 |
| GET | `/tenants/{id}/members/{member_id}/permissions` | `tenant:member:read` | 有效权限 |
| PUT | `/tenants/{id}/members/{member_id}/roles` | `tenant:member:manage` | 替换角色 |
| PATCH | `/tenants/{id}/members/{member_id}` | `tenant:member:manage` | 启停 |

角色接口仍用 V2.3.1。

## 5. 前端页面

- `/erp/system/members` 成员列表、搜索、状态筛选、添加、改角色、启停、详情抽屉
- `/erp/system/members/:memberId` 详情深链；切租户回到列表
- `/erp/system/roles` 角色列表、新建自定义角色、编辑名称/描述/权限勾选

按钮按 `tenant:member:manage` / `tenant:role:manage` 控制，不按角色名判断。

Query Key：`['tenant', tenantId, 'members' | 'roles' | 'permissions' | 'member' | 'context']`

## 6. 核心技术点

- `require_permission` 仍是唯一 HTTP 权限依赖。
- 添加/改角色先校验全部角色 ID，再写库；失败整单回滚。
- OWNER 成员不能通过成员接口改角色或被授予 OWNER。
- 前端隐藏 OWNER 选项只是 UX；后端 40321 / 40322 才是边界。
- 租户切换沿用 `epoch` 重挂载 + `isolateTenantQueries`，不 `destroyApp`。
